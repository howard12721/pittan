# pittan 実装順序と受入条件

設計日: 2026-09-12。サーバーとPC / Mobile UIを実装済み。下記は受入条件の一覧であり、全項目合格を意味しない。実施済み・未実施を[検証記録](design-docs/005-verification.md)で区別する。

## 1. 実装する順序

各段階で、実際に動く機能を通してから次へ進む。Figma再現と通信を別々に完成させて最後に初めて接続する進め方は避ける。

PCを先に完成させる優先順位は維持する。まず段階0〜7のPC対象を完了させ、その後、下表のMobile配置・操作・比較を同じ順で追加する。段階1の時点で状態をレイアウトから独立させ、後からスマホ配置へ移せる構造にする。下表は両対応までの作業をまとめたもので、PCの受入をMobileの完成待ちにはしない。スマホ版の完成判定にはiOS / Androidの実機確認を含める。

| 段階 | 作るもの | 完了条件 |
| --- | --- | --- |
| 0. Discord接続の実証 | Vite / Fastify / Dockerの最小構成、認証、在室検証、WS、SQLite、nginxとの接続 | 2人が同じActivityに入り、instanceIdに基づく同じroomへ接続。他roomの要求は拒否。Docker再起動後もroomを復元 |
| 1. デザインの土台とロビー | tokens、fonts、Tabler、Figma固有SVG、Button、PC Header / Mobile下部ナビ、RoleIcon、ParticipantRow、ロール変更 | PC 1280×800、Mobile 390×844 / 360×640のロビーを比較。12人表示の末尾まで操作でき、複数クライアントで人数・ロールが一致 |
| 2. 一つのお題を遊ぶ | お題投稿Dialog / Sheet、開始、匿名割当、入力、提出、取消、ホストによる一斉公開 | 10人が同時提出してもホスト操作前は非公開で、公開操作後に一度だけ公開。本人以外の未公開本文・対応表が通信にない。両レイアウトの入力・待機・公開を比較し、スマホのキーボード表示で送信できる |
| 3. お題の進行と管理 | queue、マウス / touch D&D、削除確認、次のお題、HistoryBrowserのお題別表示と選択シート | D&Dと投稿・削除が競合してもお題が消失しない。次のお題に進んでも匿名割当と過去回答が保持され、縦スワイプとハンドル操作が干渉しない |
| 4. 正体予想 | 回答者別履歴、予想候補、自己行固定、重複候補防止、完了・完了取消、Mobile匿名IDタブと候補シート | タブ・履歴・幅の切替中も予想が保持され、全員の完了人数が一致。ホスト / 非ホストで操作権限が分かれる |
| 5. 結果と振り返り | 正体公開、採点、実名カード、2種類の振り返り、再プレイ | 回答者はN−1、閲覧者はN問として採点。公開後のみ対応表が届く。新セッションへ旧操作が適用されない |
| 6. 障害と運用 | 切断復帰、ホスト移譲、中断、保存期限、backup、migration、graceful shutdown | 再起動・ACK欠落・復元試験に合格。既存nginx配下でidle接続が維持される |
| 7. 全体受入 | 全画面比較、長文・人数・resize、負荷試験、実際のDiscord内試験 | 以下の全受入条件を満たす |

段階0で外部公開の入口やDiscord権限がまだ用意されていない場合も、同じプロトコルのローカル実装とUI作成は進められる。ただしDiscord対応済みの証拠にはしない。

## 2. 必須テスト

### ゲームルール: Vitest

- 初回入室でLOBBYを持つsessionが作られ、同じinstanceへの入室で重複しない。
- ロール・ホストを独立して扱う。閲覧者ホストでも進行できるが回答できない。
- 開始条件、全提出後のホスト公開条件、公開後取消禁止、未完了の結果発表確認を検証する。
- ID割当は全単射で、セッション中・再接続・再起動で不変。固定乱数を注入できるテストと本番の暗号学的乱数を分ける。
- 予想の重複候補を拒否し、自分を除外して採点する。未選択と採点対象外を区別する。
- 中断・再プレイでsessionIdが変わり、旧sessionの操作が新ゲームへ入らない。
- 80 / 140文字境界、日本語、絵文字、結合文字、改行、空白、4KiB制限を検証する。

### 情報境界: DTOと実際の通信

- すべてのphase × role × hostでRoomViewを生成し、秘密の値・フィールドが存在しないことを検証する。
- 任意の他人の回答本文に識別用文字列を入れ、公開前のsnapshot / history / ACK / error / logに出ないことを検証する。
- 開示許可以外の同じ秘密状態の変更が、公開projectionを変えないことを確認する。件数や公開済み本文など許可された差分は区別する。
- ホストにも他人の未公開回答・対応表が返らない。
- 他人のsession、topic、anonymousId、memberIdを混ぜた要求を拒否する。
- 切断した旧参加者のtoken、期限切れticket、使用済みticket、偽のactorIdで認証を突破できない。
- 公開前のHTML、DOM、bundle、ログに人物と匿名IDの対応が混ざらない。

### DB / WebSocket統合

実際の一時SQLiteファイルとローカルサーバーを使う。DBやトランザクションをmockして競合試験を済ませない。

- 10接続から提出を同時送信し、公開前は回答本文がなく、ホスト操作後に回答行が10件・公開遷移が1回である。
- 最後の提出と取消の両順序を再現し、仕様の通りに確定する。
- D&D / create / delete / round.nextを競合させ、queueに重複・欠落が生じない。
- DB commit後・ACK前に停止し、復旧後の同じcommandIdが二重適用されない。
- 複数ウィンドウから同じ本人が予想を保存し、古いversionが上書きしない。
- hostEpochが変わった後に旧ホストの操作を拒否する。
- 慢性的に受信できない接続を切り離し、他接続が止まらない。
- SQLITE_FULL / commit失敗時に成功ACKや公開snapshotを出さない。
- 正常なACKを返した後のDB状態が再起動で失われないことを確認する。

### ブラウザとFigma

- [画面契約](DESIGN_CONTRACT.md)のPC 21参照・Mobile 32参照をfixture化し、現在のFigmaとの初回比較を行う。Mobile比較時は下セーフエリア20pxを注入する。
- Tablerの採用名・サイズ・線幅とA〜Jの対応を確認する。指定されたアイコン変更は差分記録を残し、レイアウトの不一致と混ぜない。
- その後にPlaywrightの固定baselineを登録し、デザイン差分を継続検知する。
- 2つのbrowser contextで提出→公開→予想→結果→振り返りを完走する。
- PC幅とMobile幅のcontextを同じroomへ入れ、同じphase・回答・完了人数が両構成へ反映されることを確認する。
- 10人分の画面を検証し、カード・候補・参加者一覧の末尾へスクロールできる。
- 140文字の回答、80文字のお題、長い表示名、同名ユーザー、絵文字を試す。同名候補はUIで識別できる補助表示を用意する。
- 下書き中に履歴へ移動して戻る、refresh、送信失敗、再接続で本文が消えない。
- D&Dをマウス・キーボード・タッチで行い、削除確認のキャンセルと確定が動く。長押し前のスワイプ・pointer cancel・一覧端のauto-scrollも確認する。
- EnterのIME確定で送信されない。Tabの順序とモーダルのfocus復帰が正しい。
- 1024×640、1280×800、1440×900、1600×900で操作要素が到達可能。
- Mobileの390×844・360×640で比較し、430×932・768×1024・844×390でもシート、A〜J、10人の最後の候補、長文が操作可能。
- 1023/1024pxの境界を入力中・予想中・シート表示中にまたぎ、本文・選択・choicesを保持し、二重接続や二重送信が起きない。
- 下セーフエリア0/20/34pxと左右inset、利用可能高さの縮小でナビやシートが内容を隠さない。狭幅・ソフトキーボードの補助状態はFigma未定義として別baselineを持つ。

### Discord内の受入

別々の実ユーザーによるDiscord Desktop / Web / iOS / Androidで確認する。SDK mockやPlaywrightの端末エミュレーションでは代替しない。

- 同じActivityは同じroom、同じchannelで別に起動したActivityは別room。
- 認可拒否・再認可、OAuth失敗、Activity Instance APIの遅延・失効を扱える。
- URL Mapping経由でHTTP / WS / SVG / フォントが読み込める。
- iframe内のCSP、nginxのヘッダー、resize、スクロール、ポップオーバーに問題がない。
- 回答者10人で一斉公開を確認する。10人の全員が実ユーザーで参加できない段階は、実機少人数 + 10接続統合試験という検証範囲を明記する。
- 10分の無操作、短いネットワーク切断、サーバー更新後も正しく復帰する。
- iOS / Androidで日本語IMEの変換、キーボード開閉、入力中の回転、予想シートの最終候補、タッチD&D、ナビのセーフエリアを確認する。
- バックグラウンド化・画面ロック・PIP/gridからの復帰、Wi-Fiとモバイル回線の切替後に最新snapshotへ戻る。未確定操作を二重適用しない。
- 開発用ApplicationでiOS / Androidを有効にして検証する。本番は合格したプラットフォームだけを有効にし、未検証のスマホ版を完成扱いにしない。

## 3. CIとリリース

PRでは型チェック、ドメイン・情報境界テスト、DB / WS統合、ビルド、固定環境の画像回帰を実行する。全画像baselineの自動更新は禁止し、差分をレビューして更新する。

ビルドはmulti-stage Dockerfileで実施する。ブラウザbundleへserverコード・秘密の環境変数が含まれないことを確認し、Linux用依存を含むimageを作る。新しい依存やランタイム更新時はローカルと本番のNode系統を揃える。

リリースはDBバックアップ→旧app停止→migration→新app起動→readiness→2クライアントで接続確認。初期構成では複数appを同時に書き込み可能な状態で起動しない。

## 4. 運用受入

| 試験 | 合格条件 |
| --- | --- |
| 10部屋×32接続の負荷 | サーバーcommit p95 50ms以内。event loop・memory・送信量も記録 |
| 同一roomで一斉提出 | 10回答者、結果の二重確定・状態分裂が0件 |
| 再接続 | ネットワーク復帰後10秒以内に最新状態が表示される |
| バックアップ | 稼働中に整合したbackupを作れ、別DBへ復元できる |
| 復元 | schema、session、匿名割当、回答、予想が整合する |
| ディスク不足 | 成功と誤認させず、復旧後に再試行できる |
| 保持期限 | 無人24時間で部屋を、再プレイから24時間で旧sessionを消す。バックアップは7日で失効 |
| 運用記録 | token、回答、予想、匿名対応を含まない |

サーバーのCPU、RAM、ディスク、回線は未確認である。数字は測定して初めて達成と判断する。バックアップ先・公開ドメイン・具体的なnginx接続設定はデプロイ時に実環境へ合わせる。

## 5. 初回リリースの完了判定

**対象プラットフォームでゲームが最後まで遊べること、匿名情報が守られること、FigmaとTabler採用契約を満たすこと、切断・再起動から戻れることを全て満たして完了とする。** PC先行の受入結果とMobileの受入結果は分けて記録し、PC合格だけで両対応完了としない。

画面だけのmock、単一クライアントの動作、ビルド成功、Figmaからのコード生成だけでは完了扱いにしない。
