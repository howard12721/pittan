# サーバー・保存・運用

2026-09-12。Fastify 1プロセスとSQLiteを採用。公開範囲を制御するprojectionと、全変更を一つの同期トランザクションにまとめるRoomsを分離した。認証主体は接続から決定し、コマンド内の人物指定で変更しない。公開前の対応表と他人の未提出本文はDTOへ含めない。

コマンドはUUIDと内容ハッシュを保存し、commit後にACKを返す。再送は同じUUIDを利用する。phase、queue、個人の編集、hostの世代を別々に照合し、古い画面からの操作を拒否する。公開・採点・新セッション作成はトランザクション内で確定する。

WSは同一Origin、一度限りの30秒ticket、5秒の認証期限を持つ。認証は8時間で失効。Discord Activity Instanceの在室者をBot APIで確認し、15秒キャッシュ、60秒周期再確認、通信障害時のみ既知参加者の5分猶予を設ける。自動ホスト移譲は切断60秒後。入室順が同じ時刻になった場合はSQLiteの挿入順を使う。

終了時はタイマーを停止し、ソケットを閉じてからDBを閉じる。切断コールバックが閉鎖済みDBを触らないよう終了フラグを共有する。無人24時間と退役セッション24時間の期限を保持する。

バックアップはSQLite online backupで整合したコピーを取り、AES-256-GCMで暗号化する。鍵は環境変数で与え、バックアップに保存しない。7日を超えた本ツールのバックアップのみ削除する。復元は認証タグとSQLite整合性を検証してから、存在しない別ファイルへ出力する。

初期実装でVitestの主要ケースが通過。その後の追加を含む件数は[検証記録](005-verification.md)へ記載。実際のSQLiteファイル、10本のTCP WebSocket、公開前の秘密、同時提出、古い編集、再起動後の再送、保存失敗時rollback、予想・採点、入室ticket、移譲・保存期限を検証した。Discord内・自宅Linux・nginx経由の実測とは区別する。Dockerfile/Composeは1レプリカ、localhost公開、既存nginxへ接続する構成とする。
